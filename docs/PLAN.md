# 水浒角色对话系统 · 开发方案

## 0. 一句话定义

用户选角色聊天（1v1 或群聊），关系由用户自定义，有文本和语音，会话彼此隔离。角色按原著设定说话，但**不重演剧情**——用户拨动时间线，改变的是「此刻的世界状态」，不是让用户去经历书里的事件。

已确认：作品《水浒传》，100 回本，首发 12 个角色，正史模式。

---

## 1. 产品形态

首页是沉浸式舞台：作品背景图 + 角色立绘卡片。点角色进 1v1，勾选多个角色进群聊。角色卡点开显示人物小传、当前状态（此刻在哪、在做什么）、关系网、开场白与音色试听。

三条主线入口：

1. **找谁聊** —— 角色列表 / 场景入口
2. **改关系** —— 关系网编辑器（含用户自己的位置）
3. **我是谁** —— 用户人设 + 时间线设置

与 AI 西湖的关键差异：他们用的是公有领域历史人物，关系由史料固定；我们用的是小说角色，**关系可被用户改写**，所以关系引擎是技术护城河，聊天框不是。

## 2. 四个核心抽象

### 2.1 角色卡 Character Card

稳定不变的设定层，也是 prompt 的稳定前缀（便于命中 prompt cache，直接省钱）：

- 身份与世界观、性格、语言风格与口头禅
- 知识边界说明、禁用行为（不出戏、不谈 AI、不剧透）
- **底线字段**：什么情况下角色不会让步（防止恋爱线把角色写成舔狗或 OOC）
- 音色 ID、立绘、开场白、3–5 条典范台词（few-shot）

角色卡要版本化。改动卡面时，老会话仍应保持当时的行为一致，否则用户会觉得角色「变了个人」。

### 2.2 关系图 Relationship Graph

节点是「角色 + 用户」，边是**有向**的：A→B 与 B→A 是两条独立的边，允许不对称。「A 恨 B 但 B 仍爱 A」正是这类产品的核心乐趣，模型里必须能表达。

每条边存：

| 字段 | 说明 |
|---|---|
| label | 关系标签：师徒 / 血仇 / 结义兄弟 / 暗中倾慕 |
| ~~closeness / trust / wariness / affection~~ | ~~亲疏、信任、戒备、好感~~ **2026-09-16 作废**：关系只用 label + 生效区间表达 |
| private_note | 只有 from 自己知道的内心话（「其实已认出他是仇人，但装作不知」） |
| is_known_to_target | 对方是否意识到这层关系 |
| valid_from / valid_to | 生效区间，指向时间锚点 |
| source | canon（原著）或 user（用户覆盖） |

**覆盖规则**：主键为 `(from, to)`，用户建的边直接盖掉原著边，UI 并排显示「原著：师徒｜你改为：反目」。反向边不会自动同步——A 改成反目，不代表 B 也这么想，除非用户主动改。

**注入规则**：不要把整张关系图丢给模型。只渲染当前会话参与者之间、以及参与者与用户之间的边，用自然语言模板拼成「你对 A：表面恭敬，暗中提防」。

### 2.3 会话 Session

`direct`（1v1）或 `group`（群聊），各自独立的成员表、消息序列、摘要和场景状态。会话之间完全隔离。

群聊由「场景 + 成员」组成，系统校验成员是否处于同一时空（见 §7.2）。

### 2.4 记忆 Memory

分三条通道，绝不混用：

| 通道 | 作用域 | 示例 |
|---|---|---|
| 会话记忆 | 仅本窗口 | 「我们刚才说到你要下山买酒」 |
| 角色记忆 | 角色 × 用户，跨窗口 | 「这个人和我说过怕水」 |
| 会话摘要 | 本窗口的长程压缩 | 每 N 轮滚动生成 |

默认 1v1 是私密的：群聊成员只能听到群内对话 + 自己和你私聊的内容。可提供「把这段私聊告诉 X」的显式同步动作——这本身就是很好的玩法，也是天然的付费点。

## 3. 时间线系统（核心）

### 3.1 定位

时间线不是剧情回放，而是**世界状态的切片**。选到第 40 回，系统不是让用户体验劫法场，而是告诉所有角色：此刻宋江刚上山、梁山已成气候、你和谁认识、和谁有仇、眼下在做什么。对话永远发生在「当下」，只是这个「当下」可以拨动。

**推进时间线的语义**：原著该发生的事照常发生，你和角色之间的私人关系与记忆随身携带。你在第 10 回和林冲喝过酒，到第 71 回他还认得你。这就是沉浸感的来源。

### 3.2 章节是 UI，事件锚点是数据

不要按 120 回逐回建模：工作量爆炸，且大部分章节的世界状态没有变化。底层用 12 个事件锚点，UI 上仍呈现为一条章回滑块。

| # | 章回 | 锚点名 | 世界状态 | 群聊氛围 |
|---|---|---|---|---|
| 1 | 第 2 回 | 九纹龙大闹史家村 | 高俅刚掌权，天下尚算太平，梁山只是王伦的小寨 | 报家门、攀交情，多数人互不相识 |
| 2 | 第 7 回 | 豹子头误入白虎堂 | 林冲蒙冤下狱，鲁智深在东京 | 不安、试探、说话留三分 |
| 3 | 第 10 回 | 林教头风雪山神庙 | 林冲被逼落草，梁山之主仍是王伦 | 人人自危，狠话多，交心少 |
| 4 | 第 16 回 | 智取生辰纲 | 晁盖等七人聚义，生辰纲被劫，官府震怒 | 江湖义气、密谋、互相试探底细 |
| 5 | 第 19 回 | 林冲火并王伦 | 晁盖成为梁山之主，梁山开始收人 | 新主旧部，站位与投名状 |
| 6 | 第 23 回 | 景阳冈武松打虎 | 武松成名，宋江在柴进庄与其结义 | 英雄相惜、敬酒、说江湖事故 |
| 7 | 第 31 回 | 血溅鸳鸯楼 | 武松成行者流亡，梁山势力扩张 | 亡命气重，仇与退路 |
| 8 | 第 40 回 | 江州劫法场 | 宋江上梁山，梁山成气候 | 兄弟相认、商议对付官府 |
| 9 | 第 50 回 | 三打祝家庄 | 梁山粮草充实，宋江主事渐明 | 议事、排兵、争功 |
| 10 | 第 71 回 | 梁山泊英雄排座次 | 108 人聚齐，梁山全盛 | 议事、排座次、争论招安 |
| 11 | 第 82 回 | 全伙受招安 | 梁山归顺朝廷，身份由寇转官 | 前途未卜，主和主战对立 |
| 12 | 第 100 回 | 神聚蓼儿洼 | 征方腊之后，十去七八 | 追忆与悼亡（见 §7.4） |

### 3.3 一个锚点决定四件事

每次用户拨动时间线，都要重新派生这四项：

**其一，关系的默认值。** 关系边带生效区间，例如「林冲 → 高俅」在第 2 回前是上下级，第 10 回后是血仇。查询区间覆盖当前锚点的那条边，用户自定义边优先。

**其二，角色的知识边界。** 防止穿帮的关键。prompt 里明确写「你只知道第 X 回之前发生的事」，角色不主动引用未来。有个很好玩的衍生效果：用户告诉第 10 回的林冲「你将来会病死在六和寺」，林冲不会恍然大悟，只会当你说了疯话。实现上把知识分两层——锚点内的原著知识，加上本次会话中用户明确告知的内容。

**其三，角色的当前状态。** 「最近在干什么」靠这个字段回答。每个角色在每个锚点存一条日常状态，例如第 40 回的武松是「在二龙山练刀，惦记着哥哥」，第 71 回的李逵是「在聚义厅守着，等哥哥发话」。这个必须人工校准，纯靠模型编会崩。

**其四，群聊氛围。** 从世界状态派生。第 71 回的聚义厅和第 2 回的大名府街头，说话方式完全不同。

## 4. 用户覆盖与原著共存

同一组 `(from, to)`，用户建的边盖掉原著边。但时间线推进时要处理冲突：你把林冲和高俅设成「结义兄弟」，推进到第 10 回时原著关系已变成血仇，系统应提示「原著关系已变化，你的设定是保留、还是从此刻起失效」。

用户覆盖支持三种语义：

| scope | 含义 | 适用场景 |
|---|---|---|
| `timeline_point` | 仅当前锚点生效 | 一次性场景扮演 |
| `from_here` | 从当前锚点起持续 | 默认推荐，推进剧情不会前后矛盾 |
| `always` | 全时段覆盖 | 用户明确想改写整部书的关系 |

默认用 `from_here`。

## 5. 用户自身相关的三层设定

这三层经常被混为一谈，必须分开：

1. **用户人设**（我是谁）：姓名、身份、背景、外貌，全局生效，所有角色对你的初始认知。
2. **用户与角色的关系**（我和他是什么）：由用户显式声明，走关系边模型，可以不对称（你当他是兄弟，他防着你）。
3. **角色对角色的关系**（他和他是什么）：原著给默认值，用户可覆盖。

> **2026-09-16 修订**：上面第 1 条里的「用户人设」提升成了**身份（persona）**，一个账号在一个作品里
> 可以有多个身份（玉娆 / 苏娘 / 路人张三），可以创建、切换、修改；关系、会话、记忆都挂在身份上，
> 时间线仍挂在账号上（世界时间是同一个）。第 2 条里的「用户与角色的关系」也定为**双向**：
> 用户→角色（我怎么看他）与角色→用户（他怎么看我）分别记录，且由人设语义解析产出初始值。
> 详见 [DECISIONS.md](../DECISIONS.md) 2026-09-16 的三条。

### 5.1 情境选项：给用户一个"做出动作"的落点（F26，2026-09-16 新增）

当角色**明确提出要求/条件**时（要凭证、要银子、要你发誓、要你跟他走），系统给出 3~4 个行动选项，
外加输入框供用户自定义动作。例：林冲说「玉佩拿来我看」→ 给他玉佩 / 不给 / 说丢了 / 说根本没有 /
自己打字「我直接把玉佩甩到他脸上转身就走」。

- **只在角色明确提要求时出现**，不是每轮都给——每轮都弹会把对话变成点选游戏。
- 选项之间**没有最优解**：每一条都是同等有效的扮演路径，不是"答对答错"。
- 自定义动作作为 `narration` 消息进历史，并参与关系演化判定（"甩过去"既是给了玉佩，也是态度恶劣）。
- 规格与约束（复用一次调用、落 `messages.meta`、先在试验台落地）见
  [DECISIONS.md](../DECISIONS.md) 2026-09-16「情境选项」。

## 6. 恋爱与好感度（**2026-09-16 作废**）

> 本节整节作废：用户明确取消好感度系统，同时取消「和角色谈恋爱」这条功能线。
> 关系强度不再用数值表达，改由 `relationship_edges` 的**标签 + 生效区间**表达；
> 「关系变了」靠写一条新的边版本来记录。理由与约束见 [DECISIONS.md](../DECISIONS.md)
> 2026-09-16「取消好感度与恋爱线」。下面保留原文，只为说明当初为什么这么想。

这是最容易做砸的部分，单独成层。**角色↔角色的原著关系**和**用户↔角色的个人关系**是两套数据，不要混用。

用户↔角色走互动累积：

```
陌生 stranger → 相识 acquaintance → 熟识 familiar → 交心 confidant → 亲密 intimate → 恋人 lover
```

态度数值（好感 / 信任 / 戒备）随对话变化，阈值到了才解锁下一阶段。**不能纯靠模型自由发挥**，否则结果一定是角色变舔狗或者 OOC。

同时每个角色有「底线」字段约束恋爱线边界。林冲在妻子被害前后的态度完全不同；在原著语境下，武松对潘金莲这条线必须表现为排斥。用户硬推时，角色应该用符合性格的方式拒绝或岔开，而不是照单全收。这个字段写好了，产品质感就和套皮聊天机器人拉开距离。

好感度跨时间线延续（`user_character_relations` 不随时间线重置），这正是「他记得你」的来源。

## 7. 四个必须提前想清楚的陷阱

### 7.1 正史模式 vs 野史模式

首期只做**正史模式**：锚点固定，用户互动只改关系和记忆，不改原著大事。野史模式（用户的举动能改写后续状态）会让状态组合爆炸，后期有余力再做。

### 7.2 空间合理性

梁山线和市井线（西门庆、潘金莲、王婆）的时间不同步。第 71 回把潘金莲和武松拉进一个群聊是不成立的。

方案：群聊由「场景 + 成员」组成，系统校验成员是否在同一时空。不合理时给出提示，但允许用户强行开会话，标记 `is_non_canon = true`。这个标记会进入 prompt，让角色知道「这是一次不太可能的相遇」。

### 7.3 未登场角色

第 2 回武松还没登场。角色可用性分四档：

| availability | 说明 | 处理 |
|---|---|---|
| `introduced` | 已登场 | 按原著给关系与状态 |
| `not_introduced` | 尚未登场但存在于世 | 关系为空，由用户自定义；群聊时自然出现「你是谁」的效果 |
| `hidden` | 不应提前唤醒 | 默认不可选 |
| `deceased` | 此刻已死 | 默认不可选，仅野史模式可唤 |

是否允许提前唤醒由用户开关 `allow_early_characters` 控制。

### 7.4 结局锚点的可用性问题

第 100 回时，首发 12 人中宋江、李逵、吴用、卢俊义、林冲、鲁智深、史进均已亡故，潘金莲、西门庆、王婆更早已死于第 26 回前后，仅武松（六和寺出家）与高俅尚在。

也就是说第 12 个锚点几乎是一座空城。这是数据正确的必然结果，产品上要提前定义它的用途：作为「尾声 / 追忆」特殊场景，或在该锚点默认开启野史模式。**不要让它成为用户滑到底部时的一次挫败体验。**

## 8. 技术架构

### 8.1 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js + TypeScript + Tailwind + framer-motion | 立绘动效、舞台转场、SPA 体验 |
| 状态 | zustand + TanStack Query | 会话态与请求缓存分离 |
| 后端 | FastAPI（Python） | 记忆抽取、RAG、评测脚本生态最好 |
| 数据库 | PostgreSQL 15 + pgvector | 关系图 + 向量检索同库，事务一致 |
| 缓存 | Redis | 会话热数据、限流、生成锁 |
| 存储 | S3 / OSS | 音频、立绘 |
| 实时 | SSE（文本）+ WebSocket（语音） | 文本流式与音频流式需求不同 |

### 8.2 模型层必须做成可替换接口

三个 Provider 抽象：`LLMProvider` / `TTSProvider` / `ASRProvider`。

成本策略：角色对话用强模型 + prompt caching；**发言调度和记忆抽取用小模型**，这一项就能差一个数量级。

### 8.3 单轮生成流水线

```mermaid
flowchart LR
  A[用户输入 文本/语音] --> B[会话与参与者装配]
  B --> C[关系解析 用户覆盖优先]
  C --> D[记忆与原著知识检索]
  D --> E{群聊?}
  E -->|是| F[发言调度 决定谁说几句]
  E -->|否| G[单角色生成]
  F --> G
  G --> H[流式文本 + 分句 TTS]
  H --> I[后处理 抽取记忆 / 更新关系标签]
  I --> J[写回会话 / 角色记忆 / 关系状态]
```

## 9. 群聊设计

群聊成败全在发言调度，做不好就会退化成「轮流念台词」。

两种模式：

- **导演模式**：LLM 当 director，决定谁开口、是否插话、本轮最多几人说话
- **自由模式**：@ 谁谁答，未 @ 则按相关性选择

必须做到的细节：

- 允许角色**沉默**，允许**抢话和打断**
- 同一轮最多 1–3 个角色发言，不能人人有份
- 关系差的两个角色应该有冲突，而不是互相附和

工程取舍：每个发言者都该看到前面发言者的输出（串行生成，真实但慢）。折中做法是**并行生成发言意图，串行生成具体表达**。

## 10. 语音方案

**输入**：按住说话 → VAD 断句 → 流式 ASR → 文本进主流程。

**输出**：LLM 出句就立即送 TTS，音频分片顺序推给前端播放队列。

唯一重要的指标是**首句延迟 ≤ 1.5 秒**，全篇时长没那么关键。

- 每个角色绑定固定音色；情绪可由文本情感标签驱动
- 用户开口时立即打断播放
- 群聊中不同角色音色必须可区分，否则用户分不清谁在说

## 11. 分期计划

| 期 | 内容 | 周期 | 验收标准 |
|---|---|---|---|
| 0 | 数据模型 + 12 角色卡 + 12 锚点 + 1v1 文本闭环 | 3–5 天 | 能选林冲聊第 10 回，回答符合处境 |
| 1 | 时间线锚点 + 关系默认值 + 用户人设 + 会话隔离 + 基础记忆 | 1–2 周 | 拨动到第 40 回，林冲对高俅的态度自动变化 |
| 2 | 群聊调度（含场景与空间校验） | 1.5–2 周 | 3 人群聊不出现轮流念台词 |
| 3 | 语音输入输出 | 1.5–2 周 | 首句延迟 ≤ 1.5 秒，可打断 |
| 4 | 时间线滑块 UI + 关系网编辑器（~~好感度系统~~ 2026-09-16 作废） | 1–2 周 | 用户改的关系被双方正确感知 |
| 5 | 沉浸式呈现 + 角色一致性评测集 | 1–2 周 | 每角色 30 条探针题，OOC 率达标 |

MVP 划线：**第 1 期结束即为 MVP**。语音和沉浸式舞台往后放，因为「文本 1v1 + 时间线 + 关系覆盖」决定了产品是否成立，其余都是加分项。

## 12. 质量保障：角色一致性评测集

每个角色准备 30 条探针问题，覆盖：

- 语言风格（会不会用现代词、称呼对不对）
- 知识边界（问未来事件时应表现为不知 / 不信）
- 关系反应（面对仇人 / 结义兄弟 / 陌生人的态度差异）
- 底线（被硬推时的拒绝方式；2026-09-16 起不再特指恋爱线）

每次改角色卡或换模型都跑一遍，作为回归测试。这是把「角色扮演」做成产品的必要投入。

## 13. 数据模型要点

完整 DDL 见 [db/schema.sql](../db/schema.sql)，基础数据见 [db/seed.sql](../db/seed.sql)。

核心表：

| 表 | 作用 |
|---|---|
| `works` | 作品与版本（100 回本） |
| `timeline_anchors` | 时间锚点，含 world_state 与群聊氛围 |
| `characters` | 角色卡（可版本化） |
| `character_lore_chunks` | 原著知识库，带生效锚点 + 向量 |
| `anchor_character_states` | 每个角色在每个锚点的状态与可用性 |
| `story_events` / `event_witnesses` | 事件与知情者，派生知识边界 |
| `relationship_edges` | 有向关系边，含时序区间与 canon/user 双源 |
| `user_personas` | 用户人设 |
| `user_timeline_settings` | 当前锚点、正史锁、提前唤醒开关 |
| `user_character_relations` | 用户↔角色的互动记录（互动次数、初识锚点、里程碑；~~好感度、阶段~~ 2026-09-16 作废） |
| `sessions` / `session_members` / `messages` | 会话与消息，会话之间完全隔离 |
| `memories` / `session_summaries` | 分层记忆 |
| `relationship_changes` | 关系变化审计，可解释「他为什么突然冷淡了」 |

### 关系生效的解析规则

给定用户当前锚点，取 `valid_from <= 当前锚点 < valid_to` 的边，然后**用户边优先于原著边**。该逻辑已固化为视图 `v_effective_relationships`，应用层直接查询，避免各处重复实现。

## 15. 已知问题与技术债

第 0 期实现完之后确认存在的问题，按优先级排列：

1. **角色卡的未来信息泄露。** `characters.identity` 是按全书视角写的（例如林冲那条含「后为马军五虎将之一，坐第六把交椅」），在第 2、10 回这类早期锚点会把未来透给模型。当前靠 prompt 里的一段兜底提示压制，但这只是缓解。正确解法是把角色卡拆成两层：**恒定层**（出身、性格、说话方式，全书不变）与**时间线状态层**（此刻的身份、已知信息，本来就存在 `anchor_character_states`）；`identity` 字段只保留恒定层，全书性的生平概览挪到单独的运营字段，不进 prompt。列入第 1 期。
2. **群聊没有发言调度。** 上下文装配已按多人在场的形状写好，但 responder 目前只是取第一个角色。第 2 期补导演模式与自由模式。
3. **记忆层未接入。** `memories` 与 `session_summaries` 两张表建好了但没人写；当前上下文只有最近 24 条原文。第 1 期接入。
4. **用户覆盖只覆盖了角色↔角色。** `v_effective_relationships` 目前只解析角色之间的边；用户自己与角色的显式关系声明（`from_kind='user'`）还没接进 prompt，暂时只有互动累积的 `user_character_relations`。
5. ~~**`user_character_relations` 不会衰减。**~~ **2026-09-16 关闭**：好感度已整体取消，这条问题随之消失。
6. **pgvector 未装时向量列降级为 jsonb。** 仅影响 RAG 与记忆检索，本地开发不受阻。
